# v2.1 数据可视化规划

> 状态：v2.1 候选范围  
> 基准：v2.0.0 已聚焦赛事成绩追踪；v2.1 在不扩张产品主线的前提下，补齐更清晰的数据理解能力。

## 一、版本目标

v2.1 的主线建议定为“赛事数据可视化增强”。目标不是新增复杂功能，而是让用户更快理解赛事走势、赛段结构和分类榜变化。

v2.1 应继续服务当前核心用户路径：赛事首页 → 赛事详情 → 赛段成绩 → 分类榜 → 车手/车队详情。

## 二、建议纳入范围

### 1. GC 时间差走势增强

当前代码已经出现 GC 时间差走势图能力，v2.1 可以把它整理为稳定功能。

建议能力：

- 展示前 5-10 名 GC 车手随赛段变化的时间差
- 支持选择单个车手高亮
- 支持赛段节点点击，跳转对应赛段成绩页
- 空数据时提供明确说明，而不是隐藏模块

### 2. 赛事赛段结构图

赛事详情页当前已有总距离、平均距离、长赛段数量、休息日、赛段类型分布等轻量分析，可以升级为可视化模块。

建议能力：

- 赛段类型分布图：Flat / Hills / Mountain / ITT / TTT
- 赛段距离柱状图：突出最长赛段、ITT/TTT、山地赛段
- 休息日/关键赛段标记
- 点击赛段图表项跳转赛段详情或成绩页

### 3. 分类榜变化趋势

优先从 GC 开始，随后再扩展到冲刺、爬坡、青年榜。

建议能力：

- 展示领骑衫持有者随赛段变化
- 展示冲刺/爬坡积分前几名的积分变化
- 对并列、缺失数据提供稳定 fallback

### 4. 车手详情可视化

不做复杂“骑行数据对比”，只做车手个人历史表现的轻量图表。

建议能力：

- 近期成绩排名趋势
- 领奖台/前十统计
- 参赛赛事分布

## 三、范围边界

以下内容不属于数据可视化规划：

- 复杂实时电视转播级数据面板
- 需要新增重型 BI / 图表后台的能力

## 四、实现优先级

P0：GC 时间差走势稳定化，补齐空状态、异常状态、跳转链路。

P1：赛事详情页赛段结构可视化，复用现有 stages 数据，不新增复杂表结构。

P2：领骑衫/分类榜变化趋势，优先使用已有 jerseys 和 classification 表。

P3：车手详情轻量统计图，仅在数据足够时展示。

## 五、技术建议

小程序端优先使用轻量自绘或原生组件组合，避免引入重型图表依赖导致包体和兼容性风险。数据计算尽量放在后端或页面加载时一次性预处理，避免频繁 `setData`。

后端可以优先新增聚合接口，而不是让前端多次拉取原始表后自行拼接。例如：

- `GET /api/v1/races/:id/visualization/overview`
- `GET /api/v1/races/:id/visualization/gc-trend`
- `GET /api/v1/races/:id/visualization/jersey-timeline`

如果短期不新增接口，也可以先在赛事详情页复用现有 stages、jerseys、gc 接口完成轻量版本。

## 六、验收标准

v2.1 可视化能力应满足：

- 不影响 v2.0.0 核心成绩查询链路
- 无数据、半数据、异常接口时都有清晰降级
- 小程序包体仍低于审核风险线
- 首屏不因图表计算明显变慢
- 用户可以从图表回到具体赛段或成绩页

## 七、推荐下一步

先做一个最小闭环：赛事详情页新增“赛段结构”模块 + GC 页面稳定“时间差走势”。这两项都基于当前已有数据和代码雏形，收益高、范围可控。
